## Question

Review `src/pyauditor/excel/` (`capa.py`, `report.py`, `consolidate.py`, `glosas.py`, `orgao_consolidation.py`) against the `python-production-engineer` skill's checklist (`.agents/skills/python-production-engineer/SKILL.md`). Read every file in the package in full before writing findings.

Judge specifically:

- `openpyxl` workbook construction: any resource leaks (workbooks opened, never closed), any silent overwrite of user-entered data (this repo has a documented invariant that re-running `consolidate` must preserve the fiscal's manual decision columns — verify the code that reads them back is defensive against a workbook someone hand-edited into a broken shape).
- Duplicated Code across `report.py` and `consolidate.py` (both build similar sheet structures) — is there a real extraction opportunity, or is the duplication load-bearing (different sheet semantics)?
- Error handling: `glosas.py`'s JSON ledger read/write (`glosa_historico.json`) — is a corrupted or hand-edited ledger file handled gracefully?
- Money/points arithmetic: floats vs. `Decimal` for glosa percentages and payment calculations — any accumulation risk worth flagging (even if not worth fixing here)?
- Security: any path traversal risk in filenames derived from `competencia`/`orgao` (user-influenced strings used to build output paths)?

Report each finding as `file:line — severity — description — suggested fix`, ordered by the skill's priority list. Run `uv run ruff check src/pyauditor/excel` and `uv run mypy src/pyauditor/excel` first, note the baseline, don't re-report what's already clean.

## Answer

### Tooling baseline

- `mypy src/pyauditor/excel` — clean (`Success: no issues found in 8 source files`).
- `ruff check src/pyauditor/excel` — 34 findings, all either cosmetic (RUF001/002/003 "ambiguous" `×`/`−` in Portuguese math notation in docstrings/comments — correct on purpose, not worth fixing) or line-length E501s, plus a handful of real smells that are folded into the findings below rather than re-listed verbatim: `consolidate.py:369` B007 unused loop var, `consolidate.py:389` F841 unused `bold`, `consolidate.py:450` B905 `zip` without `strict=`, `report.py:205-206` F841 unused `tipo_col`/`status_col`.

All files in the package were read in full: `capa.py`, `_style.py`, `groups.py`, `glosas.py`, `orgao_consolidation.py`, `report.py`, `consolidate.py`. Call sites in `cli/report.py`, `cli/consolidate.py`, `cli/main.py`, `cli/measure.py` were also inspected to judge the security and resilience findings, since the excel package's read/write functions are only as defensive as their callers let them be.

### Findings

**Correctness / data loss**

1. `src/pyauditor/excel/consolidate.py:158-161` — Medium — `_clean()` silently transcodes every string cell (headers and all row values, including fiscal/gestor free text like Justificativa and Observação do Gestor) through `.encode("cp1252", errors="replace").decode("cp1252")`. Any character outside Windows-1252 (smart quotes pasted from a PDF, emoji, names with non-Latin script) is silently replaced with `?` — no warning, no log. `report.py`/`capa.py` don't do this transcode at all, so identical fiscal-entered text behaves differently depending on which sheet built it. — Fix: drop the transcode (openpyxl/modern Excel handle UTF-8 fine — this looks like defensive code for an era that no longer applies) or, if some legacy constraint still requires it, log a warning listing which cells got mangled instead of failing silently.

2. `src/pyauditor/excel/consolidate.py:389` (ruff F841) — Low — `bold = label in ("Total de Pontos", "Valor Glosa")` is computed but never read; `label_cell.font = Font(bold=True)` is applied unconditionally two lines below, so every row in the GLOSAS summary block ("Fórmula...", "Limite", "Percentual Aplicado") renders bold, not just the two intended rows. Visible cosmetic bug from what looks like an incomplete refactor. — Fix: `label_cell.font = Font(bold=True) if bold else BODY_FONT`.

3. `src/pyauditor/excel/consolidate.py:120-155` (`read_existing_decisions`) and `src/pyauditor/excel/capa.py:143-160` (`read_capa_fields`) — Medium — this is the ticket's specific "hand-edited into a broken shape" concern. The header-name-driven `col_idx` lookup (`consolidate.py:136`) is good practice (doesn't assume fixed column positions), but a hand-edited workbook with a duplicate/renamed header (e.g. two "Indicador" columns, or a stray column literally named "Justificativa" inserted by a fiscal) makes the dict-comprehension silently keep the *last* matching column index — decision values then get read from the wrong column with no error or warning. The only validation is "does 'Indicador'/'Órgão' appear somewhere in row 1" (`consolidate.py:134,139`); duplicate/misaligned columns aren't detected. — Fix: raise (or at least warn-and-skip) when a `_DECISION_COLUMNS`/`Indicador`/`Órgão` name appears more than once in the header row, rather than silently keeping the last occurrence.

4. `src/pyauditor/excel/report.py:205-207` (ruff F841) — Low — `tipo_col = 3` / `status_col = 8` are computed as if they were the source of truth for the data-validation ranges, then never used — the actual ranges are hardcoded as string literals `"C2:C{max_row}"` / `"H2:H{max_row}"` (`report.py:215,223`). If `_EVIDENCIAS_COLUMNS` is ever reordered, these validations will silently attach to the wrong column, and the dead variables make it look like there's a safeguard when there isn't one. — Fix: derive the range strings from `tipo_col`/`status_col` (e.g. via `openpyxl.utils.get_column_letter`) so reordering `_EVIDENCIAS_COLUMNS` can't silently desync the validation target.

5. `src/pyauditor/excel/consolidate.py:450` (ruff B905) — Low — `zip(range(2, len(_CALCULO_COLUMNS) + 2), colunas)` relies on both sequences having the same length by convention (currently 3 and 3); without `strict=True`, a future edit to `_CALCULO_COLUMNS` or the `colunas` tuple (`consolidate.py:435`) that changes one but not the other silently truncates output columns instead of raising. — Fix: add `strict=True`.

**Security**

6. `src/pyauditor/excel/consolidate.py:353-360,369-373` — Medium — fiscal/gestor-entered free text (Justificativa, Observação do Gestor, Decisão Fiscal, Número da Ocorrência) round-trips from the previous consolidado workbook straight into new cells via `_write`/`ws.cell(value=...)` with no check for a leading `=`, `+`, `-`, or `@` — the classic Excel/CSV formula-injection vector. If any of that text was ever pasted from an external source and starts with one of those characters, it becomes a live formula the next time someone opens the regenerated `.xlsx`. Given this is the one column set explicitly designed to persist across runs, it's also the one most likely to accumulate copy-pasted text over the contract's lifetime. — Fix: when writing string values that start with `=+-@`, prefix with a literal marker (e.g. leading apostrophe) or force the cell's format to `@` (text) before writing.

7. `src/pyauditor/cli/main.py:238,252`, consumed by `excel/report.py:build_report` and `excel/consolidate.py:build_consolidated_workbook`'s caller in `cli/consolidate.py` — Low — output paths are built as `f"relatorio_{competencia}_{orgao}.xlsx"` / `f"relatorio_{competencia}_consolidado.xlsx"`, and `cli/report.py:81`/`cli/consolidate.py:45` build `roms_dir / competencia` — all from the `competencia` CLI positional, which (unlike `orgao`, constrained by argparse `choices=("MinC","MTur","both")` at `main.py:108-109`) has no format validation at the `report`/`consolidate`/`run` entry points. `cli/measure.py:93` already validates competência against `_COMPETENCIA_RE = r"^\d{4}-\d{2}$"` but that check isn't reused for `report`/`consolidate`. A value like `../../etc` would let the `.xlsx` output or the ROM-summary read escape the intended `reports/`/`roms/` directories. Low likelihood in practice (single-operator local CLI, not network-facing), but cheap to close and this package is exactly where the resulting file write/read happens. — Fix: validate `competencia` against the existing `_COMPETENCIA_RE` at every subcommand's entry point, not just `measure`.

**Resilience**

8. `src/pyauditor/cli/consolidate.py:92-96` (`read_capa_fields`, `read_existing_decisions`) and `src/pyauditor/cli/report.py`'s `read_capa_fields` call — Medium — neither call is wrapped in a `try/except`, unlike the `glosa_historico.json` read at `cli/report.py:108-113`, which explicitly catches `(OSError, json.JSONDecodeError)` and degrades gracefully (rollover defaults to 0, warning logged). A genuinely corrupt/unreadable `.xlsx` — not just an unexpected sheet shape, but e.g. a previous run that crashed mid-`save()`, or a file saved with the wrong extension — makes `load_workbook` raise a raw `zipfile.BadZipFile`/`openpyxl.utils.exceptions.InvalidFileException` straight out of `run_consolidate`/`run_report`, bypassing the module's own `_error(...)` domain-error path entirely. This directly undercuts the ticket's "hand-edited into a broken shape" concern — shape drift (missing sheet/columns) is handled (`consolidate.py:129-140` returns `{}`), but file-level corruption is not. — Fix: wrap the `read_capa_fields`/`read_existing_decisions` calls in `cli/report.py`/`cli/consolidate.py` in the same `try/except (OSError, ...)` → `_error(...)`/graceful-degrade pattern already used for the JSON ledger.

9. `src/pyauditor/excel/capa.py:139`, `report.py:394`, `consolidate.py` (`workbook.save(...)`, called from `cli/consolidate.py:107`/`cli/report.py`) — Low/Medium — saves write directly to the final path, not atomically (no write-to-temp-then-rename). A crash or power loss mid-`save()` can leave a truncated/corrupt `.xlsx` at the exact path that `consolidate` reads back on its *next* run (`read_existing_decisions(output_path)`) — which, per finding 8, isn't caught gracefully, so one bad run can brick the next run's ability to consolidate at all until the file is manually removed. — Fix: save to a `.tmp` path in the same directory and `os.replace()` into place, for both `report`'s and `consolidate`'s outputs.

10. `src/pyauditor/excel/glosas.py:122-124` (`write_historico`) — Low — same non-atomic-write pattern as finding 9, lower impact since the one caller (`cli/report.py:108-113`) already tolerates a corrupted result gracefully on the next read (falls back to `{}`/rollover-0 with a warning). Noting for consistency rather than as an independent risk.

**Compatibility / operability**

11. `src/pyauditor/excel/capa.py:150` and `src/pyauditor/excel/consolidate.py:128` (`load_workbook(path, data_only=True)`) — Low — neither result is closed (no `with`, no `.close()`); the same is true of every `Workbook()` built in `capa.py`/`report.py`/`consolidate.py` before `.save()`. Confirmed via `grep -rn "\.close()" src/pyauditor` — zero matches anywhere in the codebase. For today's one-shot CLI process this is harmless (the OS reclaims file handles/memory on exit), but it's worth flagging per the skill's explicit-resource-lifecycle principle, especially since `consolidate`/`report` are exactly the kind of code that could end up wrapped in a longer-lived batch loop or service later. — Fix: `with load_workbook(path, data_only=True) as wb: ...` (openpyxl's `Workbook`/loaded workbooks support the context-manager protocol) or an explicit `.close()` in a `finally`.

**Missing / fragile tests**

12. `tests/test_glosas.py` — Low — no test feeds `glosas.read_historico` a malformed/corrupted JSON file directly; the graceful-degradation behavior currently exists only because the one caller (`cli/report.py:108-113`) happens to wrap the call — there's no test proving `read_historico` itself does anything sane (or that the caller's catch is still wired up) if `glosa_historico.json` is hand-edited into invalid JSON.
13. `tests/test_excel_consolidate.py`, `tests/test_capa.py` — Low — coverage exists for "no GLOSAS sheet" / "no Indicador column" (`read_existing_decisions`'s early returns), but nothing covers the duplicate-header-name collision (finding 3) or a genuinely corrupt/non-zip `.xlsx` (finding 8) — both would currently either silently misbehave or crash uncaught, respectively, with no regression test to catch a fix or a regression.
14. No test exists for the formula-injection concern (finding 6) — expected, since the guard itself doesn't exist yet.

**Clarity / maintenance**

15. `src/pyauditor/excel/report.py:77-82,148-166` vs `src/pyauditor/excel/consolidate.py:164-182,262-265` — Low — `_UNIT_BY_SHAPE` is a byte-for-byte-identical dict literal duplicated in both files; `_new_sheet`/`_write_row` (report.py) and `_new_sheet`/`_write` (consolidate.py) are near-identical boilerplate (consolidate.py's version additionally runs every value through `_clean()`). This is genuine incidental duplication with a real drift risk — a new `shape` added to the engine has to be remembered in two places, and does not need to be duplicated for semantic reasons the way `_inms_base_row`/`_INMS_BASE_COLUMNS` legitimately does (report.py's version carries fiscal-manual/evidence columns that consolidate.py's per-órgão-pooled view intentionally omits — that duplication *is* load-bearing and shouldn't be merged). — Fix: extract `_UNIT_BY_SHAPE` and the sheet/row-writing helpers into a small shared module (or `_style.py`, already shared by both files) — leave `_inms_base_row`/columns alone.

16. `src/pyauditor/excel/glosas.py` (`compute_glosa`), `src/pyauditor/excel/consolidate.py:350-399,450-464` — Informational, not a bug — money/points arithmetic uses plain `float` throughout, no `Decimal`. At this system's realistic magnitudes (contract values in the hundreds-of-thousands to low-millions of reais, percentages to 2-4 decimal places, at most a few hundred summed penalty-point rows per competência) float64's ~15-17 significant digits keep accumulation error far below the 2-decimal rounding already applied everywhere values are displayed — not worth introducing `Decimal` today. One thing worth a one-line code comment rather than a fix: the per-row `valor_glosa` in GLOSAS (`consolidate.py:351,356`) is rounded to 2 decimals for display, but the aggregate "Valor Glosa" total (`consolidate.py:377`) is computed independently from the unrounded `total_pontos` rather than by summing the displayed rows. That's the *correct*, safer design (avoids compounding row-level rounding into the total), but it does mean a fiscal manually summing the visible GLOSAS rows on the sheet won't exactly match the printed total — could read as a bug to an auditor unless documented.

**Style**

No additional findings beyond the ruff baseline noted above (RUF001/002/003 unicode-ambiguity warnings on Portuguese math notation are correct as written and not worth "fixing"; E501 line-length hits are cosmetic).
