Judge specifically:

### Findings

1. `src/pyauditor/orchestration/state.py:42-49` — **Resilience/operability, Major** — `load_state` does `json.loads(...)` then `raw["commands"]`/`CommandStateEntry(**entry)` with no error handling. A corrupted or hand-edited run-state file (bad JSON → `json.JSONDecodeError`; missing `"competencia"`/`"commands"` key → `KeyError`; extra or missing field on an entry → `TypeError: unexpected/missing keyword argument`) propagates raw, uncaught, through `_ensure_state` (`run.py:114`) and `execute_run`, all the way to `cli/run.py:31`'s `run_run` (no try/except there either) and `cli/main.py` (no global handler around command dispatch). Result: a bare Python traceback instead of an actionable message, for a file the design doc explicitly expects users/tools might hand-edit or that could be left in a bad state after a crash mid-write. Ticket's specific question ("actionable error, or raw KeyError/JSONDecodeError up through execute_run?") — confirmed: raw exception, not actionable.
   Fix: wrap the parse in `load_state` with `try/except (json.JSONDecodeError, KeyError, TypeError) as exc: raise RunStateCorruptedError(path) from exc` (or equivalent), with a message telling the operator the state file's path and that deleting it starts the run over — preserve `from exc` per the skill's "falha explicita" rule.

2. `src/pyauditor/orchestration/state.py:1-7` (module docstring) — **Concurrency, Minor** — Design doc `.scratch/interactive-cli/issues/03-run-orchestrator-and-resume.md` (Answer, "Concorrência") explicitly accepts "sem trava de arquivo" as a deliberate scope cut for two processes targeting the same `(competencia, orgao)` file. The code's behavior matches that decision (no locking anywhere in `save_state`/`load_state`), but nothing in `state.py` — module docstring or function docstrings — says so. A future maintainer reading `save_state`/`load_state` in isolation has no signal this is intentional rather than an oversight; ticket specifically asked to confirm the code carries the comment, not just matches the behavior.
   Fix: add one line to the module docstring or `save_state`, e.g. "No file locking — concurrent writers to the same state file are an accepted scope cut (design ticket 03: single-user CLI, not high-concurrency), not built preventively."

3. `src/pyauditor/orchestration/run.py:226-244` vs `run.py:269-287` — **Resilience/duplication, Moderate; verdict: worth extracting** — Confirmed still true: the pre-dispatch dependency-missing branch and the post-dispatch `Result.status == "error"` branch each independently (a) build an `error` `CommandStateEntry`, upsert+save+notify, (b) call `on_failure`, (c) on `"skip"` build a `skipped` entry, upsert+save+notify, cascade, break, (d) on anything else (`"abort"`, or fallthrough) return `RunResult` early. ~18 lines duplicated with only a cosmetic difference (pre-dispatch nests `retry` inside a combined `skip-or-retry` `if`; post-dispatch keeps `retry` and `skip` as separate sibling `if`s — same behavior, different shape, which itself is a small readability tax when comparing the two blocks). Verdict: at this size, extraction is warranted, not "acceptable as-is" — two independent reasons beyond pure line-count: (i) it's the *second* real call site in the same function, which is exactly the bar the skill sets before introducing an abstraction ("nao criar abstracoes sem segundo caso de uso real" — the second case already exists here); (ii) per finding 5 below, the pre-dispatch copy has **zero test coverage**, so the two copies can silently drift (e.g. a future edit to add a log line or a state field lands in the post-dispatch copy and is forgotten in the pre-dispatch one) with nothing to catch it.
   Fix: extract `_record_failure_and_decide(command, orgao, request_ctx, state, path, error_entry, on_state_change, on_failure, cascade) -> tuple[RunState, FailureDecision]` (or similar) that does build-error-entry→save→notify→ask→(skip: build-skipped-entry→save→notify→cascade)→return decision; both call sites reduce to computing the `error_message` and interpreting the returned decision (`retry` → `continue`, `skip` → `break`, else → `return RunResult(...)`).

4. `src/pyauditor/orchestration/run.py:218-222` — **Idempotency, confirmed safe (no fix needed)** — Ticket asked to verify `execute_run` re-run against a fully-`done` state is a true no-op. Confirmed by inspection: for an entry with `status in ("done", "skipped")` the loop body does `continue` before `dependency_missing`, `save_state`, or `_dispatch` are ever reached — no re-dispatch, no unnecessary state-file write. Confirmed by test `tests/test_orchestration_run.py:83-95`, which asserts zero `on_state_change` calls on a second `execute_run` against an all-`done` state. No action needed.

5. `src/pyauditor/orchestration/run.py:222-247` — **Tests, Major** — The entire pre-dispatch dependency-missing failure branch (error-entry creation, `on_failure` call, skip+cascade, retry-loop, abort-return) is at 0% coverage per `--cov-report=term-missing` (lines 222, 227-247 all listed as missing). Cross-checked against `tests/test_orchestration_run.py`: every failure-path test (`test_execute_run_cascades_skip_to_downstream_commands`, `test_execute_run_abort_stops_immediately_and_preserves_pending`, `test_execute_run_retry_re_dispatches_until_success`) drives failure via a hard-failure CSV that makes `measure` *run* and return `Result.status == "error"` — i.e. they all exercise the **post-dispatch** branch only. Nothing constructs a scenario where `dependency_missing` itself returns non-empty (e.g. selecting `report` when `bootstrap`/`measure` haven't produced output, or resuming after an external process deleted an upstream artifact) — this is a real, reachable resume scenario per the design doc, not defensive dead code, and it's the exact code this ticket's finding 3 says should be merged with the other branch — right now neither branch is protected by a shared test.
   Fix: add a test selecting a downstream command (e.g. `report` only, via `request.commands`) with no upstream `bootstrap`/`measure` output present, and assert: entry status becomes `error` with the "dependência não satisfeita" message, `on_failure` returning `"skip"` cascades to skip `consolidate`/later steps, and `on_failure` returning `"abort"` stops immediately with the entry preserved as `error` (not overwritten).

6. `src/pyauditor/orchestration/run.py:80-88, 174-188, 292-309` (`_plan`'s `"both"` branch, `_downstream`'s consolidate special-case, `_cascade_skip`) plus `run.py:165-171` (`_dispatch`'s `consolidate` branch) — **Tests, Major** — No test anywhere in the repo (`tests/test_orchestration_run.py`, `tests/test_orchestration_summary.py`, `tests/test_cli_run.py`) constructs a `RunRequest` with `orgao="both"`. That's the more complex path: phase-major fan-out across two órgãos, `consolidate` depending transitively on *both* órgãos' `report`, and the cross-órgão cascade-skip case in `_downstream` (`later_command == "consolidate" and command in ("bootstrap","measure","report")`, `run.py:183-185`) — entirely unexercised. `_capa_path_for`'s `orgao == "both"` branch (`run.py:76`) is likewise untested. This is exactly the kind of path most likely to hide a latent bug precisely because it's never run.
   Fix: add at least one `orgao="both"` happy-path test (both órgãos succeed, consolidate runs last) and one where one órgão's `measure` fails and is skipped, asserting `consolidate` cascades to `skipped` too (exercising the `later_command == "consolidate"` branch of `_downstream`).

7. `src/pyauditor/orchestration/summary.py:72-80, 108` (`_next_steps`, the "Próximos passos" `Panel`) — **Tests, Moderate** — 0% coverage on `_next_steps`'s body (lines 77-79) and the `Panel` render (line 108); `tests/test_orchestration_summary.py` only exercises the single-órgão, all-`done` happy path. `_next_steps` re-invokes `dependency_missing` and does string formatting that plausibly regresses silently (wrong field, wrong join) with nothing to catch it; it's also the second call site of `dependency_missing` outside `run.py`, worth a contract test independent of `execute_run`.
   Fix: add a test with at least one non-`done` entry (e.g. `report` pending because `measure` was skipped) and assert the "Próximos passos" panel text appears with the expected dependency-missing reasons.

8. `src/pyauditor/orchestration/summary.py:96` (`_STATE_ICON[entry.status]`) — **Resilience, Minor, compounds finding 1** — `CommandState` is a `Literal` type, not validated at runtime; `load_state` (finding 1) will happily construct a `CommandStateEntry` with any string in `status` from a hand-edited file. If such a state file survives past `load_state` (e.g. a typo'd status that isn't outright malformed JSON), `render_summary` raises a raw `KeyError` from `_STATE_ICON[entry.status]` instead of surfacing the earlier, more actionable corruption. Same root cause as finding 1 (no runtime validation at the JSON boundary), different failure site.
   Fix: covered by fixing finding 1 with real validation (e.g. checking `status` against `get_args(CommandState)` in `load_state`), rather than a separate fix here.

9. `src/pyauditor/orchestration/summary.py:44-51` (`_result_for`) vs `summary.py:54-69` (`_artifact_line`) — **Clarity, Minor** — Confirmed: this is a mild Repeated Switches (Fowler) smell. `_result_for` discriminates the four `CommandResult` subtypes via a `command → type` dict lookup plus one `isinstance`; `_artifact_line`, called immediately below with the same `entry` and the `result` `_result_for` just found, re-discriminates the same four subtypes via a 4-way `isinstance` chain. Every `render_summary` iteration answers "which Command result is this" twice. Not urgent — it's two functions, four branches each, all in one file — but since this is exactly the second occurrence the skill wants before flagging a smell (not before fixing it), it's worth recording.
   Fix (optional, non-blocking): fold `_artifact_line`'s isinstance chain into a `dict[type, Callable[[object], str]]` table keyed the same way as `_RESULT_TYPE_FOR_COMMAND`, or have `_result_for` hand back the matched formatter directly so the type is discriminated once per entry instead of twice.

### Summary verdict

Ruff/mypy clean as expected. `state.py` is small and 100%-covered but has the review's most consequential gap: no runtime validation at the JSON-file boundary (findings 1, 8) — the one place this package reads untrusted/mutable input. The duplicated retry/skip/abort handling in `execute_run` (finding 3) is confirmed still present and, combined with the pre-dispatch branch's total lack of test coverage (finding 5), is worth extracting now rather than deferring. The `"both"`-órgão path (finding 6) is the single biggest test-coverage blind spot in the package — it's the code that actually differs in complexity from the single-órgão case and it has never been run by a test. Idempotency (finding 4) is verified correct and needs no work.
