## Question

Dentro de `excel`, `report.py` (workbook por órgão) e `consolidate.py`/`orgao_consolidation.py` (fusão multi-órgão MinC+MTur) formam sua própria fronteira: `consolidate` lê/funde a saída de múltiplas execuções de `report` (um por órgão). Rastreie: o que `consolidate` assume sobre a estrutura de cada workbook de órgão que `report` gera (nomes de aba, ordem de coluna, tipos de célula) sem revalidar; o que acontece se os dois órgãos estiverem em versões de schema diferentes (ex.: um relatório gerado antes de uma mudança de coluna); e se o parâmetro de rateio MinC/MTur (ver `CONTEXT.md`) é lido de forma consistente nos dois lados. Não repita achados de qualidade interna já cobertos em `.scratch/production-readiness-review/issues/03-excel-package-review.md` — foque só na travessia entre `report` e `consolidate`.

Aplique o skill `python-production-engineer` (ler `.agents/skills/python-production-engineer/SKILL.md` por inteiro) para julgar severidade. Achados citam `file:line`.

## Answer

### The surprising shape of the boundary

`consolidate.py`/`orgao_consolidation.py` do **not** actually read `report.py`'s `INMS_BASE`, `GLOSAS`, group-tab, or `EVIDENCIAS` sheets. `cli/consolidate.py:_load_summaries` (`src/pyauditor/cli/consolidate.py:47-54`) sources every indicator-level number straight from `roms/<orgao>/<competencia>/*.json` (the same `IndicatorSummary` artifact `measure` writes), bypassing `report.xlsx` entirely for that data. `orgao_consolidation.with_orgao_consolidation` (`src/pyauditor/excel/orgao_consolidation.py:33-54`) operates purely on in-memory `IndicatorSummary` objects, never on a workbook. So the two independently-hardcoded `_INMS_BASE_COLUMNS` tuples (`src/pyauditor/excel/report.py:40-67` vs `src/pyauditor/excel/consolidate.py:260-265`) look like a shared contract but aren't one — each module builds its own `INMS_BASE` sheet from the same `IndicatorSummary` source, so they can never desync from *reading* each other; only from independently drifting in what they choose to display (already noted as load-bearing, non-mergeable duplication in the prior review's finding 15). This narrows the real boundary to two things: (1) `capa.py`'s `CAPA_E_CONTROLE` round-trip through `report.xlsx`, and (2) file/dir *existence* checks. Both have real gaps, below.

### Findings

**1. Correctness / silent data loss — fiscal's manual "Rateio" edit in `CALCULO_PAGAMENTO` is discarded on every `consolidate` rerun.** `src/pyauditor/excel/consolidate.py:408-413` (`build_calculo`) takes `rateio_minc`/`rateio_mtur` parameters defaulting to `RATEIO_PADRAO = 0.5` (`consolidate.py:54`), but the only call site, `build_consolidated_workbook` at `consolidate.py:504`, never passes them — every `consolidate` run writes `0.5/0.5` unconditionally. Unlike `GLOSAS`'s `_DECISION_COLUMNS`, which `read_existing_decisions` (`consolidate.py:147-186`) explicitly preserves across reruns (ticket 04 Q3's documented contract), there is no equivalent read-back for `CALCULO_PAGAMENTO` — nothing in `capa.py` or `consolidate.py` ever reads a previous consolidado's rateio cells. CONTEXT.md states "Rateio MinC/MTur ... Entrada do fiscal, não calculada pelo pipeline," but there is no code path anywhere (`capa.py:FIELD_LABELS`, `report.py`, `consolidate.py`) through which a fiscal's rateio value can durably survive a `consolidate` rerun — any value hand-typed into `CALCULO_PAGAMENTO!B5:B6` is silently overwritten back to 0.5/0.5 the next time `consolidate` runs. This is the single highest-severity finding for this boundary: it is exactly the kind of manual-edit-clobbered-on-rerun bug the `GLOSAS` preservation contract was built to prevent, but the protection wasn't extended to the sibling sheet holding the same class of fiscal input. Fix: either read `CALCULO_PAGAMENTO`'s prior rateio cells back (mirroring `read_existing_decisions`) before rewriting, or add "Rateio MinC"/"Rateio MTur" to `capa.py`'s `FIELD_LABELS` so it round-trips through the same mechanism as `Valor mensal vigente`.

**2. Correctness / schema drift — a stale órgão's `CAPA_E_CONTROLE` silently loses the disagreement warning, not just the value.** `build_capa` (`src/pyauditor/excel/consolidate.py:189-247`) only warns when *both* órgãos return a non-`None` "Valor mensal vigente" and they disagree (`consolidate.py:216-219`). If one órgão's `report.xlsx` was generated by an older code/label version — e.g. `capa.py:FIELD_LABELS` (`capa.py:29-52`) gained/renamed a field after that órgão's report was built weeks earlier — `read_capa_fields` (`capa.py:146-176`) simply won't find that label text within its scan window and returns the field absent from the dict; `_as_float(None)` (`consolidate.py:479-480`) then returns `None`, and `build_capa` falls back to the other órgão's value **with zero warning**, because the warning is gated on both sides being present. This is exactly the "one report generated before a column change" scenario the ticket asks about, and it degrades silently instead of loudly. Fix: warn whenever exactly one órgão's capa is missing "Valor mensal vigente" (not only when both are present and disagree) — a missing field on one side of a two-órgão fusion is itself signal that the workbooks are unequal vintages.

**3. Compatibility / weak boundary contract — "dependency ready" checks existence only, not shape.** `check_consolidate_ready` (`src/pyauditor/cli/consolidate.py:33-42`) checks `report_dir / f"relatorio_{competencia}_{orgao}.xlsx"` with `.exists()` and `roms_dir / orgao / competencia` with `.is_dir()` — no check that the xlsx has a `CAPA_E_CONTROLE` sheet, or that the ROM JSONs parse against the current `IndicatorSummary` shape. A `report.xlsx` produced months ago by different code (missing sheet, or ROM JSONs missing a field `IndicatorSummary` now requires) is reported "ready," and the real failure only surfaces downstream as a caught-but-opaque exception (`cli/consolidate.py:100-103`: `except Exception as exc: ... "falha ao ler workbook Excel"`, or `_load_summaries`'s `TypeError`→`ValueError` at `cli/consolidate.py:47-54`). Not a crash risk (both paths are wrapped), but the pre-flight check gives false confidence rather than naming the actual incompatibility. Low/Medium — worth a one-line note in the error path (which sheet/field was expected) rather than a structural fix.

**4. Adjacent, not this boundary — `IndicatorSummary` version drift between órgãos is a `rom.summary`/`consolidate` concern, not `report`/`consolidate`.** `_load_summaries` is duplicated verbatim in `cli/report.py:47-54` and `cli/consolidate.py:47-54`, both doing `IndicatorSummary(**raw)` against `roms/<orgao>/<competencia>/*.json`. If MinC's ROMs were measured weeks before MTur's, with a dataclass field added/removed by an intervening code change, a hard field mismatch raises `TypeError`→caught `ValueError`→clean CLI error (good, not silent) — but a *compatible* change (new field with a default) would let an older MinC JSON silently supply the default with no warning that the two órgãos' summaries come from different `measure` code generations. Noting for completeness since it's precisely the drift scenario asked about, but the actual read/parse boundary is `rom/summary.py` ↔ `measure`/`report`/`consolidate`, not `excel/report.py` ↔ `excel/consolidate.py` — out of this ticket's file scope.

**5. Informational — the one real cross-workbook read (`CAPA_E_CONTROLE`) is well-encapsulated.** `render_capa_sheet`/`read_capa_fields` (`capa.py:66-116`, `146-176`) are the single shared source of truth for both writing and reading that sheet, used identically by `bootstrap`'s standalone capa, `report.py`'s embedded capa, and `consolidate.py`'s two `read_capa_fields` calls (`consolidate.py` via `cli/consolidate.py:92-93`). Because `read_capa_fields` keys by label text found within its scan window rather than by fixed row/column position, it tolerates `FIELD_LABELS` reordering and (up to the window-size caveat in finding 2) added/removed fields without misaligning existing labels. This is good boundary design and the reason `report.py`↔`consolidate.py` has fewer real coupling defects than the ticket's framing implied — the risk is concentrated in the two gaps above (missing-value warning gating, and rateio's total lack of a persistence path), not in raw structural assumptions about column order or cell type.
