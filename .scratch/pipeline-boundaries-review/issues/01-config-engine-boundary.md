## Question

O pacote `config` (`manifest.py`, `catalog.py`, `models.py`, `catalogs/anexo_e.yaml`) expõe um schema de manifesto/catálogo consumido por `engine` (`pipeline.py`, `quality_gates.py`, `strategies/*`) e por `cli/bootstrap.py`/`cli/measure.py`. Rastreie tudo que atravessa essa fronteira: quais campos de `DatasetEntry`/manifest o `engine` lê diretamente (sem revalidação), que suposições de shape/tipo/obrigatoriedade o `engine` faz sobre dados vindos de `config` que o `config` não garante, e onde uma mudança silenciosa (campo ausente, tipo errado, catálogo externo desatualizado) atravessaria sem erro explícito até quebrar mais adiante (ou pior, produzir número errado sem erro). Não repita achados de qualidade interna já cobertos em `.scratch/production-readiness-review/issues/01-config-package-review.md` e `02-engine-package-review.md` — foque só na travessia.

Aplique o skill `python-production-engineer` (ler `.agents/skills/python-production-engineer/SKILL.md` por inteiro) para julgar severidade. Achados citam `file:line`.

## Answer

**Baseline**: `uv run mypy src/pyauditor/config src/pyauditor/engine` — `Success: no issues found in 18 source files`. mypy strict is clean at this boundary; every finding below is something the type checker cannot see, because the crossing is `str` (column name / file name) in both directions — `config`'s Pydantic models only ever guarantee "non-empty string" (`Field(min_length=1)`), never "this string identifies a column that actually exists in the CSV `engine` will load, or a value in the unit `engine`'s arithmetic expects." Read in full: `config/manifest.py`, `config/catalog.py`, `config/models.py`, `config/_paths.py`, `config/catalogs/anexo_e.yaml`, and every file in `engine/` (`pipeline.py`, `quality_gates.py`, `strategies/{base,__init__,_filters,_numbers,_target,ratio,segmented_ratio,count_difference,external_catalog_sum,precomputed_table}.py`).

The through-line: `config` validates that a field *is a string of the right shape*; it never validates that the string *resolves to something real on the other side of the boundary* (a CSV header, a catalog id, a unit). `engine` then reads almost every config-declared column name via `dict.get(name, "")`/`row.get(name, "") or ""` rather than indexing — so a typo anywhere in a `*.yaml` indicator config doesn't crash, it silently turns into "no data for this row/column," which several shapes' own zero-activity business rules then reinterpret as **"fully compliant, no penalty."** That is a wrong number with zero explicit error, exactly what the ticket asked to trace.

### Correctness / data-loss (HIGH)

1. **`src/pyauditor/engine/strategies/external_catalog_sum.py:29-33`** — `calculation.catalog_codes_column`/`occurrence_id_column` come from `ExternalCatalogSumCalculation` (`config/models.py:211-212`), validated only as `str, min_length=1` — never checked against the CSV's actual header. Both are read via `row.get(col, "")`. A typo in `catalog_codes_column` (or an upstream CSV header rename) makes `codes_raw` empty for every row → `codes = []` → `matched = []` → `if not matched: continue` (line 32) drops the occurrence entirely → `total_points` stays `0` for the whole indicator → `conforms = total_points == 0` (line 48) is `True`. A broken config produces a "zero infractions, fully compliant" INMS 1.8 result with no exception anywhere in the pipeline. Independently: any single code in `codes` that isn't a key in `catalog` (`code in catalog`, line 31) — a stale/mistyped Anexo E id, or the packaged `catalogs/anexo_e.yaml` (`config/catalog.py`) falling behind a Termo de Referência revision — is silently filtered out with no count of unmatched codes anywhere in `memoria`. This is precisely the ticket's "catálogo externo desatualizado atravessa sem erro explícito, produzindo número errado sem erro" scenario. **Fix**: validate `occurrence_id_column`/`catalog_codes_column` against the loaded CSV's header once, at the pipeline boundary (`pipeline.measure`), before any strategy runs; and surface unmatched codes (count/list) in `memoria` instead of dropping them silently.

2. **`src/pyauditor/engine/strategies/precomputed_table.py:45-47,52,56,75-76`** — the same masking pattern, five times over in one function: `result_column`, `name_column`, `penalty_column`, `numerator_column`, `denominator_column` (all `str = Field(min_length=1)` on `PrecomputedTableCalculation`, `config/models.py:221-232` — never checked against the CSV header) are read via `row.get(col, "")` / `row.get(col, "") or ""`. A typo in `result_column` alone: every row's `raw_value` is `""` → `continue` on line 47 for every row → `categories = []`, `total_penalty = 0.0` → `conforms = total_penalty == 0.0` is `True`, `headline = 0.0`. Same "silently 100% compliant on a broken config" failure as finding 1, for a different shape — and it's the shape used by the fiscal apuração sheets, i.e. the ones most likely to be hand-edited and most likely to drift from the config's expected column names. **Fix**: same as finding 1 — validate configured column names against the CSV header before the per-row loop; raise a `ValueError` naming the missing column(s) and the config file.

3. **`src/pyauditor/engine/strategies/ratio.py:93-95`** (`aggregation: "precomputed"`) — three stacked issues at the one crossing point in this branch: (a) `calculation.precomputed_result_column` is read via bare indexing `rows[0][calculation.precomputed_result_column]`, not `.get()` — inconsistent with every other column read in the same package (findings 1-2, plus `_filters.py`/`quality_gates.py` below), so whether a config typo raises `KeyError` or silently produces `0`/`nan` depends on which shape/aggregation the author happened to pick; (b) that value is fed straight to bare `float(...)`, not `parse_decimal(...)` — the PT-BR comma-decimal parser every other numeric read in this codebase routes through (`_numbers.py`'s own module docstring: real exports use `,` as decimal separator) — so a legitimate precomputed percentage like `"87,5"` raises `ValueError: could not convert string to float: '87,5'` instead of parsing or degrading to `nan`; (c) `assert len(rows) == 1` (line 94) validates an external-data shape assumption ("exactly one row for `aggregation: precomputed`") with a bare `assert`, which is stripped under `python -O` and not actionable. **Fix**: route through `parse_decimal`; translate a missing-column `KeyError` into a `ValueError` naming the config field; replace the `assert` with a raised `ValueError`.

### Correctness / unit mismatch (MEDIUM)

4. **`src/pyauditor/config/models.py:245-248`** (`Target.value: float = Field(ge=0, le=100)`) vs **`src/pyauditor/engine/strategies/precomputed_table.py:53,66`** — `Target.value` is schema-constrained as a percentage (0-100). But `PrecomputedTableCalculation` with `result_is_percent=False` (`config/models.py:222`, e.g. INMS 1.8's PDT point-total mode) reuses the very same `target.value` as an absolute point threshold: `penalty = max(value - config.target.value, 0.0)` (`precomputed_table.py:66`). `Target` has no notion of which unit-space it's in. Concretely: any legitimate points threshold above 100 is rejected at config-load time for the wrong reason ("must be ≤ 100%" makes no sense for a points target — an accidentally-actionable failure, at least, but with a misleading message); any points threshold that happens to be ≤ 100 loads fine with a field whose declared semantics ("percentage") no longer describe its actual use, so nothing downstream (types, docs, ROM rendering) can tell which unit a given `Target.value` is in without also reading `result_is_percent` on a sibling model. **Fix**: give `Target` (or `IndicatorConfig`) an explicit unit — e.g. drop `le=100` and add `unit: Literal["percent", "points"]` consumed by `precomputed_table.py`, or split into `PercentTarget`/`PointsTarget` selected by `result_is_percent`.

5. **`src/pyauditor/config/models.py:226-228`** vs **`src/pyauditor/engine/strategies/precomputed_table.py:37`** — `numerator_column`/`denominator_column` on `PrecomputedTableCalculation` are independently optional with no `model_validator` enforcing "both or neither" — contrast with `Source._check_csv_or_dataset` (`models.py:81-89`) and `RatioCalculation._check_fields_for_aggregation` (`models.py:166-182`), which enforce exactly this kind of cross-field invariant elsewhere in the same package. If a config author sets only one of the two fields (expecting the hours-weighted pooled headline), `weighted = calculation.numerator_column is not None and calculation.denominator_column is not None` (`precomputed_table.py:37`) silently evaluates `False`, and the headline silently falls back to an unweighted arithmetic mean of per-ativo percentages — weighting was requested but silently ignored, no error or warning. **Fix**: add a `model_validator` to `PrecomputedTableCalculation` requiring both-or-neither, matching the sibling models' established convention.

6. **`src/pyauditor/engine/strategies/ratio.py:37-42`** combined with **`src/pyauditor/engine/strategies/_filters.py:21-32`** — a typo in `RatioCalculation.denominator_filter.column` (`config/models.py`'s `Filter.column: str = Field(min_length=1)` — never checked against the CSV header) makes `_matches` compare `row.get(column, "")` for every row; if the filter type never matches an empty string, every row is filtered out, `denominator == 0`, and `ratio.py`'s own "no eligible activity this competência" business rule (lines 37-42, deliberately added — per its comment — to distinguish a legitimately empty month from a failure) fires: `conforms=True, penalty_points=0.0`. A config bug becomes indistinguishable from "there was nothing to measure this month" — the exact leniency meant for real zero-activity months becomes a silent trap for config/CSV drift. **Fix**: same root cause as findings 1-2 — validate every filter/result column name against the CSV header once, at the pipeline boundary, before any strategy can reinterpret a missing column as "zero denominator."

### Resilience / misleading diagnostics (LOW)

7. **`src/pyauditor/engine/quality_gates.py:44,48`** and **`src/pyauditor/engine/strategies/_filters.py:22`** — `NotNullCheck.column`/`InSetCheck.column`/`Filter.column` (config, never checked against the CSV header) all funnel through `row.get(column, "")`. A mistyped column name in `quality_gates.checks` doesn't raise "column X not present in this CSV" — it's reported to the ROM, once per row, as `"'<typo'd column>' é nulo/vazio"` (`quality_gates.py:46`) or `"fora do conjunto permitido"` (line 50), actively misdirecting a human reviewer toward "bad source data" when the real defect is a config/CSV name mismatch. Lower severity than findings 1-3 because this path does fail loud-ish (every row gets rejected, `MeasurementResult.hard_failure` in `pipeline.py:46-52` likely trips) — but the diagnostic lies about the cause. **Fix**: distinguish "column absent from the CSV header entirely" (checked once, up front) from "column present but this row's value is empty" in the rejection reason.

8. **`src/pyauditor/engine/pipeline.py:78-84`** vs `DatasetEntry.encoding`/`Source.encoding` (`config/manifest.py:40`, `config/models.py:78`) — both validated only as non-empty strings, never checked against Python's known codec names. A typo (`"utf8-sig"` vs `"utf-8-sig"`) surfaces as a raw `LookupError: unknown encoding: utf8-sig` from `source_path.open(...)` (`pipeline.py:79`), not wrapped with the config field/file that caused it. Loud, not silent, so lower priority than the findings above — listed because it's the one other unvalidated-string-used-as-a-system-API-parameter crossing besides the path-safety one `config/_paths.py`'s `reject_unsafe_relative_path` already guards well (that guard — `manifest.py:38`, `models.py:76` — is the one part of this boundary that *is* validated defensively, and is a good pattern the column-name fields above should be made to follow).

### What's already solid at this boundary (not re-reported)

`strict=True` on every Pydantic model in `config/` means YAML `int`/`bool` values can't silently coerce into a `str` field crossing into `engine` — no type coercion leak observed. `Penalty.step_size_pct: float = Field(gt=0)` and `SegmentedRatioCalculation.step_size_pct: float = Field(gt=0)` genuinely prevent the division-by-zero `engine`'s `shortfall(...)/step_size_pct` arithmetic would otherwise be exposed to — that contract holds end to end. Dataset alias resolution (`DatasetManifest.resolve`, `manifest.py:53-66`) and unknown-`shape` dispatch (`SHAPE_REGISTRY[config.calculation.shape]`, `pipeline.py:177`) both fail loud with a `KeyError`/actionable message rather than defaulting — the column-name fields above are the outlier, not the norm.
