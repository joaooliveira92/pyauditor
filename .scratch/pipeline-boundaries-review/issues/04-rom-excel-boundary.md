## Question

`rom` (`render.py`, `summary.py`) escreve sidecars JSON (`IndicatorSummary`) que `excel` (`report.py`, `consolidate.py`) lê de volta para montar o workbook final. Rastreie a fronteira: o que `rom` serializa (campos, tipos, presença/ausência) vs. o que `excel` assume ao desserializar — já sabemos de `production-readiness-review` (ticket 04-rom) que `IndicatorSummary(**raw)` não valida tipo nenhum no load; o objetivo aqui é ir além e verificar especificamente o que quebra do lado do **consumidor** (`excel/report.py`/`excel/consolidate.py`): que aritmética/formatação assume um campo presente/numérico sem checar, e onde isso propagaria um erro incompreensível em vez de uma mensagem acionável. Cheque também competência/órgão como chave de correlação entre o sidecar e o restante do workbook — mismatch de chave é silencioso ou explode? Não repita achados de qualidade interna já cobertos em `.scratch/production-readiness-review/issues/03-excel-package-review.md` e `04-rom-package-review.md` — foque só na travessia.

Aplique o skill `python-production-engineer` (ler `.agents/skills/python-production-engineer/SKILL.md` por inteiro) para julgar severidade. Achados citam `file:line`.

## Answer

### Context / what changed since the prior reviews

`.scratch/production-readiness-review/issues/04-rom-package-review.md` (finding 4) originally reported that `IndicatorSummary(**raw)` did no type validation. That has since been fixed: `IndicatorSummary.__post_init__` (`src/pyauditor/rom/summary.py:41-53`, via `_require_str`/`_require_numeric`/`_require_bool`, `summary.py:59-80`) now rejects wrong-typed fields at load time with a `TypeError`, caught and re-raised with the offending file path by `_load_summaries` in both `src/pyauditor/cli/report.py:47-55` and `src/pyauditor/cli/consolidate.py:51-59`. Several other findings from `03-excel-package-review.md` are also already fixed (`atomic_write` + `workbook.close()` at `excel/report.py:367-370`, `excel/consolidate.py:120-124` in `cli/consolidate.py`, `capa.py:139-143`; duplicate-header detection at `consolidate.py:129-144`; formula-injection guard via `number_format = "@"` at `consolidate.py:371-372`). This review does not re-report any of that — it traces forward from the now-working type check to what still crosses the `rom`→`excel` boundary unvalidated.

All files read in full: `src/pyauditor/rom/summary.py`, `src/pyauditor/rom/render.py`, `src/pyauditor/excel/report.py`, `src/pyauditor/excel/consolidate.py`, `src/pyauditor/excel/capa.py`, `src/pyauditor/excel/glosas.py`, `src/pyauditor/excel/groups.py`, `src/pyauditor/excel/orgao_consolidation.py`, `src/pyauditor/excel/_style.py`, plus consumer call sites `src/pyauditor/cli/report.py` and `src/pyauditor/cli/consolidate.py`.

### Findings (skill's priority order)

**1. Correctness / data loss — highest priority**

- **`src/pyauditor/rom/summary.py:71` (`_require_numeric`) — High.** The type check `isinstance(value, int | float) and not isinstance(value, bool)` accepts `float('nan')`/`float('inf')`/`float('-inf')` — it validates *type*, not *finiteness*. Python's `json.loads` (called at `cli/report.py:51`, `cli/consolidate.py:55`) accepts the non-standard `NaN`/`Infinity`/`-Infinity` tokens by default (verified: `json.loads("NaN")` → `nan`, no exception), so a hand-edited or buggy sidecar with `"result_pct": NaN` sails through `IndicatorSummary.__post_init__` — despite the module's own docstring (`summary.py:21-24`) explicitly promising this class of value is "rejected here, at load time, rather than crashing deep in `excel/report.py`/`excel/consolidate.py` arithmetic." It doesn't crash there either — it does something worse. `round(float('nan'), 2)` and NaN/Inf arithmetic never raise in Python (confirmed), so the value flows unchanged through `excel/report.py:217` (`round(summary.result_pct, 2)`), `excel/consolidate.py:274`, `_faixa` (`consolidate.py:308-316`), and `build_glosas`'s running sum `total_pontos += pontos` (`consolidate.py:346-348`). I confirmed by direct test that `openpyxl` writes a NaN/Inf cell value as an **empty `<v/>` element** in the saved `.xlsx` XML — i.e. the cell silently renders **blank**, not an error, not `#NUM!`. Because `total_pontos`/`glosa_final`/`CALCULO_PAGAMENTO` (`consolidate.py:381-383`, `408-476`) are *sums over all indicators*, one indicator with a NaN `penalty_points` silently blanks the aggregate glosa/payment figures for the entire consolidated workbook — an auditor sees plausible-looking but silently wrong (or unexplainedly blank) financial cells, with zero log line, zero exception, anywhere. This is exactly the "incomprehensible failure deep in Excel-writing code" the ticket asked about, except silent rather than a crash — arguably worse. Fix: `math.isfinite(value)` in `_require_numeric`, and/or load sidecars with a `parse_constant` callback that raises on `NaN`/`Infinity`/`-Infinity` so this fails loudly at `_load_summaries`, not silently at the `openpyxl` boundary.

- **`src/pyauditor/rom/summary.py:26-39` (`IndicatorSummary` fields) — High.** There is no `competencia` field on `IndicatorSummary` — only `orgao`. `_load_summaries` in `cli/report.py:47-55` and `cli/consolidate.py:51-59` globs every `*.json` under a directory whose path already encodes the competência (`roms/<orgao>/<competencia>/`, per `cli/measure.py:99,108`) and trusts the directory placement completely — there is no field inside the sidecar itself to cross-check against. A stale sidecar left behind from a previous competência, one copied in by mistake, or a future bug in `measure`'s output-path logic writing to the wrong directory, is **undetectable**: `report`/`consolidate` build the workbook's `"Competência"` column from the *CLI argument* (`report.py:200/206` via the `competencia` parameter passed into `_inms_base_row`, `consolidate.py:267/271` likewise), not from the sidecar — so the output shows this month's competência label next to silently-wrong, stale numeric data. That is the single worst failure mode for an audit artifact: internally consistent-looking, wrong, and silent. Fix: add a `competencia` field to `IndicatorSummary`'s schema, and have `_load_summaries` assert `summary.competencia == competencia` per file (both callers already know the expected competência), raising `ValueError` naming the offending path on mismatch.

- **`src/pyauditor/cli/consolidate.py:92-93` + `src/pyauditor/excel/orgao_consolidation.py:33-54` (`with_orgao_consolidation`) — High.** Unlike competência, `orgao` *is* a field on `IndicatorSummary`, but it's likewise never cross-checked against the directory it was loaded from: `minc = _load_summaries(roms_dirs["MinC"])` and `mtur = _load_summaries(roms_dirs["MTur"])` (`consolidate.py:92-93`) trust every file under `roms_dirs["MinC"]` to genuinely be a MinC summary, without asserting `summary.orgao == "MinC"`. `orgao_consolidation.py:39` then re-keys purely by the sidecar's own `.orgao` field: `by_key.setdefault((contractual_id, asset), {})[summary.orgao] = summary`. If one file physically sitting in the MinC directory carries `"orgao": "MTur"` (copy-paste mistake, stale artifact from a manual re-run, bug elsewhere), it silently lands in the `by_orgao["MTur"]` slot and **overwrites the real MTur record** for that indicator (plain dict assignment, last write wins, no collision check) — the pooled `INMS_BASE` "Consolidado" row (`orgao_consolidation.py:70-84`) is then built from the wrong pair, with the genuine MTur figure discarded and zero warning emitted anywhere. Fix: validate `summary.orgao` against the expected órgão for the directory being loaded, at `_load_summaries` time, in both `cli/report.py` (which already threads an `expected_orgao` parameter through for other purposes but never uses it to check the loaded summaries) and `cli/consolidate.py`.

**2. Security / privacy** — no additional findings beyond what `03-excel-package-review.md` already covered (formula-injection guard already in place at `consolidate.py:371-372`).

**3. Concurrency / idempotency / transactions** — no findings; the `rom`→`excel` read path is a single-process, single-pass, no-shared-mutable-state read.

**4. Resilience / failure behavior**

- **`src/pyauditor/rom/summary.py:33-39` (`target_value`, `numerator`, `denominator`) — Low/Medium.** `_require_numeric`'s type+finiteness check (once fixed per finding 1) still wouldn't catch an out-of-range value — e.g. a negative `result_pct`, or a `target_value` several orders of magnitude off a sane percentage. Not a crash risk (openpyxl happily stores any finite float), but `_faixa` (`consolidate.py:308-316`) and `diferenca_para_meta`/`dif` (`report.py:200-203`, `consolidate.py:268-270`) will compute and display a déficit/superávit figure that reads as a legitimate audit number to a fiscal without any bounds sanity check. Lower priority than findings 1-3 since it degrades to "plausible-but-wrong number" rather than "silently blank/overwritten," but worth a light range check (e.g. `0 <= result_pct` for ratio-based shapes) if this boundary gets hardened.

**5. Compatibility / operability**, **6. Tests**, **7. Performance**, **8. Clarity**, **9. Style** — no additional cross-boundary findings; internal-quality items in these categories were already covered by the two closed `production-readiness-review` tickets and are not repeated here.
